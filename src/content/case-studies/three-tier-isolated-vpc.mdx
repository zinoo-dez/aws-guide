<section id="business-problem">
  <h2>1. Business Problem & Context</h2>
  <p>
    An enterprise SaaS company preparing for SOC2 Type II and PCI-DSS certification discovered their application servers and PostgreSQL databases were residing in a single flat VPC subnet. If an attacker exploited a remote code execution vulnerability in the public web app, they gained direct network access to the database credentials and customer records.
  </p>
</section>

<section id="requirements-constraints">
  <h2>2. Requirements & Constraints</h2>
  <ul>
    <li><strong>3-Tier Network Isolation</strong>: Strict separation of Ingress, Compute, and Persistence.</li>
    <li><strong>Air-Gapped Database Subnets</strong>: Databases must have zero internet gateway or NAT gateway routes.</li>
    <li><strong>Least-Privilege Security Group Chaining</strong>: Ingress rules reference security group IDs, never IP addresses.</li>
  </ul>
</section>

<section id="implementation">
  <h2>6. Implementation Highlights</h2>
  <DeepDiveAccordion title="Security Group Chaining Terraform Blueprint" badge="IaC Recipe">

```
# Database Security Group allowing traffic ONLY from the Application SG
resource "aws_security_group" "database" {
  name        = "prod-aurora-db-sg"
  vpc_id      = aws_vpc.main.id
  description = "Allow inbound PostgreSQL strictly from App tier"

  ingress {
    description     = "PostgreSQL from App Tier"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id] # SG Chaining!
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

<section id="takeaways">
  <h2>8. Key Architectural Takeaways</h2>
  <blockquote>
    <strong>Security Rule:</strong> Never write CIDR IP blocks (e.g. <code>10.0.10.0/24</code>) in internal application and database Security Groups. Always chain Security Group IDs to create immutable access control.
  </blockquote>
</section>
