<section id="business-problem">
  <h2>1. Business Problem & Context</h2>
  <p>
    A multiplayer mobile game with 10 million daily active users updates player scores every time a match finishes. Generating a real-time global leaderboard using relational SQL (<code>SELECT player_id, score, RANK() OVER (ORDER BY score DESC)...</code>) locked table indexes and took over 8 seconds per query.
  </p>
</section>

<section id="requirements-constraints">
  <h2>2. Requirements & Constraints</h2>
  <ul>
    <li><strong>Sub-Millisecond Rank Retrieval</strong>: Fetch the global Top 100 or a player's exact rank in &lt; 2ms.</li>
    <li><strong>Massive Write Ingestion</strong>: Process up to 100,000 score submissions/second during tournaments.</li>
    <li><strong>Zero Data Loss</strong>: Ensure historical scores survive in-memory cache restarts.</li>
  </ul>
</section>

<section id="implementation">
  <h2>6. Implementation Highlights</h2>
  <DeepDiveAccordion title="Redis Sorted Set Commands for Ranking" badge="Redis Commands">

```
# Add or update player score atomically:
ZADD leaderboard:season_5 98450 "player_u9921"

# Retrieve top 10 players instantly (Rank 1 to 10):
ZREVRANGE leaderboard:season_5 0 9 WITHSCORES

# Fetch specific player's exact rank:
ZREVRANK leaderboard:season_5 "player_u9921"
```

<section id="takeaways">
  <h2>8. Key Architectural Takeaways</h2>
  <blockquote>
    <strong>Algorithm Architecture:</strong> When data requires real-time sorted ranking, use data structures built for sorting (Skip Lists in Redis Sorted Sets) rather than forcing relational databases to sort millions of rows on demand.
  </blockquote>
</section>
