<section id="business-problem">
  <h2>1. Business Problem & Context</h2>
  <p>
    When organizations build on AWS, engineering teams often jump straight to provisioning services before clarifying quantitative constraints. A typical ambiguous request sounds like: <em>"Build us an API backend that is scalable, fast, and cheap."</em>
  </p>
  <p>
    Without architectural rigor, teams over-provision expensive dedicated instances or under-design resilience against Availability Zone outages, leading to budget blowouts and downtime.
  </p>
</section>

  <ArchitectureDiagram

  <ol>
    <li><strong>Extract Hard SLOs</strong>: Convert business language into numbers (latency, RTO, RPO, concurrency).</li>
    <li><strong>Isolate State from Compute</strong>: Ensure application compute tiers are completely stateless.</li>
    <li><strong>Evaluate Managed vs Unmanaged</strong>: Default to serverless/managed platforms unless specific runtime controls are required.</li>
    <li><strong>Audit Failure Modes</strong>: Verify how the system behaves if any single AWS AZ or service API experiences degradation.</li>
  </ol>

<section id="implementation">
  <h2>6. Implementation Highlights</h2>
  
  <DeepDiveAccordion title="AWS Organizations Multi-Account Topology" badge="Security Architecture">
    <p>
      In a production setup, you should split accounts using AWS Control Tower or AWS Organizations:
    </p>
    <ul>
      <li><strong>Management Account</strong>: Dedicated purely to billing and consolidated reporting (zero application workloads).</li>
      <li><strong>Security Tooling Account</strong>: Houses GuardDuty master, AWS Config aggregators, and central KMS keys.</li>
      <li><strong>Log Archive Account</strong>: Immutable S3 bucket holding all CloudTrail and VPC Flow Logs with Object Lock enabled.</li>
      <li><strong>Workload Accounts</strong>: Separate accounts for <code>Development</code>, <code>Staging</code>, and <code>Production</code>.</li>
    </ul>
  </DeepDiveAccordion>
</section>
